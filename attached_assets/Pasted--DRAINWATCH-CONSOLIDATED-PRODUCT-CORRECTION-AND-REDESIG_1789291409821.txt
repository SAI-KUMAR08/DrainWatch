# DRAINWATCH — CONSOLIDATED PRODUCT CORRECTION AND REDESIGN PROMPT

## IMPORTANT: READ THIS ENTIRE PROMPT BEFORE MODIFYING ANY CODE

You are upgrading the existing DrainWatch project.

The current implementation has three major problems:

1. The map looks artificial and does not resemble a real geographic map.
2. The UI and information architecture are not sufficiently polished or practical.
3. The civilian and government officer experiences are connected through the same account/application flow.

These issues must be fixed together, but they must be implemented as three clearly separated workstreams:

* **A. Realistic map redesign**
* **B. Professional UI/UX redesign**
* **C. Completely separate civilian and officer applications**

Do not confuse these requirements.

Do not merely rename existing pages or add two dashboard tabs. The result must be a properly structured civic safety platform.

## Application 1: Civilian/Public Portal

This is for ordinary citizens who want to report public hazards.

Suggested routes:

```text

 /report
 /my-reports
 /track-report
 /citizen/login
 /citizen/register
```

The civilian portal should contain:

* Public home page
* Report a hazard

* My submitted reports
* Report tracking
* Public safety alerts

Citizens must not see officer features.

Citizens must not see:

* Officer dashboard
* Government analytics
* All reports from every user
* Internal notes
* Department assignments
* News-management controls

* Other citizens' private information
* Officer settings

# 3. STRICT AUTHENTICATION SEPARATION

This is a mandatory security requirement.

Civilian and officer authentication must be separate from the user's perspective and enforced by the backend.

## Civilian accounts

A civilian can:

* Register as a civilian
* Log in through the civilian login
* Submit reports
* View their own reports
* Track their own report status
* View permitted public information

A civilian cannot:

* Access officer routes
* Access officer APIs
* View all reports
* Change their account type to officer
* Access internal analytics
* Manage report assignments
* Run news scans
* Modify risk settings

## Officer accounts

An officer must:

* Log in through the officer login page
* Have an officer account created or approved through a secure process
* Receive officer permissions only after backend validation
* Access the officer dashboard and authorized officer APIs

Public registration must never create an officer account.

Do not provide a public dropdown that allows a user to choose:

```text
Civilian
Officer
Admin
```

Do not trust a role supplied by the frontend.

Do not use a frontend variable such as:

```javascript
isOfficer = true;
```

as a security mechanism.

Do not allow a user to become an officer by editing local storage, cookies, URL parameters, or frontend state.

---

# 4. BACKEND AUTHORIZATION

Frontend route hiding is not enough.

Every officer API must validate:

* Authentication
* Token/session validity
* Account type
* Role
* Permission
* Resource access

Use separate API namespaces where practical:

```text
/api/public/*
/api/citizen/*
/api/officer/*
/api/auth/citizen/*
/api/auth/officer/*
```

Example permissions:

```text
Civilian:
  POST /api/reports                    allowed
  GET  /api/citizen/reports/mine       allowed
  GET  /api/officer/reports            denied
  PATCH /api/officer/reports/:id       denied
  GET  /api/officer/news               denied
  GET  /api/officer/analytics         denied

Officer:
  GET  /api/officer/reports            allowed
  GET  /api/officer/map                allowed
  PATCH /api/officer/reports/:id       allowed if authorized
  GET  /api/officer/news               allowed
  GET  /api/officer/analytics          allowed
```

A civilian token/session must return `401` or `403` when calling officer-only APIs.

A civilian must not be able to access `/officer/dashboard`, even by manually entering the URL.

# 16. REPORT AND MAP DATA FLOW

The intended flow is:

```text
Civilian submits a real report
        ↓
Backend validates the report
        ↓
Real coordinates are stored
        ↓
Image is analyzed by AI, if configured
        ↓
Risk engine calculates an explainable score
        ↓
Report is stored in MongoDB
        ↓
Officer map fetches the report from the backend
        ↓
Marker appears at the correct real-world location
        ↓
Marker color reflects the calculated risk level
        ↓
Officer can verify, assign, update, or resolve it
```

The report must not exist only in browser memory.

Refreshing the page must not delete reports.

The database must be the source of truth.
